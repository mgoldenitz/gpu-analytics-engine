# Decisions

- Stream compaction (flag, exclusive scan, scatter) for the filter. Output stays in input order, so it compares directly with pandas.
- Own scan is Blelloch (GPU Gems 3 ch. 39), 256 threads with 512 elements per block. No bank-conflict avoidance, to keep it readable.
- Keep `scan="cub"` (`cp.cumsum`) next to `scan="own"`, so the benchmarks compare our scan with NVIDIA's.
- The `cub` path uses the inclusive cumsum directly. The scatter subtracts 1 (`shift`), so there is no extra pass over memory.
- int32 positions: limit of 2^31 - 1 rows. 200M rows fits.
- memcheck runs with the CuPy pool off (`set_allocator(None)`), because the pool rounds allocations and hides small overruns.
- pytest cache is off (`-p no:cacheprovider`), because OneDrive locks the cache folder.
- Benchmark data is made in memory with a seed. Nothing goes to disk or into the repo.
- Timing: 3 warmup runs, then the median of 10, with `Device.synchronize` before and after each run.
- Pinned mode fills the pinned input buffer before the timer starts, as a pinned data loader would give it.
- Crossover = smallest n from which the GPU wins at that size and at all larger sizes.
- Group-by: one flat open-addressing table, linear probing (as cuCollections static_map). Capacity = next power of two >= 2x expected_groups, so the load factor is at most 0.5 and `& mask` replaces `%`.
- INT_MIN is the empty-slot key. Input with INT_MIN is rejected, not handled with a second table.
- Sums are unsigned 64-bit atomics (no signed 64-bit atomicAdd). Values are sign-extended, so two's complement gives the right signed result.
- Counts are int32 in the table (at most n < 2^31) and int64 in the output.
- Overflow sets a flag and the wrapper raises. No resize, no silent wrong result.
- Group-by benchmark: expected_groups = the true number of distinct keys (Zipf leaves some keys unused). Keys are random distinct values in [0, 2^31 - 1), not 0..g-1.
- Polars casts values to Int64 before sum, because Polars sums Int32 as Int32 and overflows. DuckDB uses `SUM(v)::BIGINT` (its SUM gives HUGEINT). pandas uses `sort=False`, as there is no ORDER BY.
- `pinned_empty` takes a dtype now, for the int64 output columns.
- Block group-by: each block takes 4096 rows (16 per thread), not 256. With one row per thread, a block sees at most 256 keys, so a 1024-slot table can never fill and there would be no fallback case to test.
- Shared table: 1024 slots x 16 bytes = 16 KB per block. A row probes at most 32 shared slots, then goes straight to the global table, so a full shared table does not cost 1024 probes per row.
- `groupby.csv` keeps one `engine` (`hash_groupby`) and adds a `strategy` column, so a filter on one column picks a strategy. CPU rows have `-`.
- Charts: GPU #76b900 (NVIDIA green), pandas #0072B2, Polars #E69F00, DuckDB red #D62728, each with its own marker shape (GPU circle, pandas square, Polars triangle, DuckDB diamond). GPU lines are solid and 2.5 wide; CPU engine lines are dashed and 1.5 wide, so the GPU stands out. GPU markers: filled = main GPU path (pinned, block), hollow = alternate GPU path (pageable, global). No legend on line charts; end labels are pushed apart in screen points so none overlap. Copy time = e2e time minus kernel_only time, so it includes allocation overhead. Uniform vs Zipf use texture, not a second hue.
- One `__device__ add_global` for both strategies and for the flush, so there is only one global probe loop.
- Input checks (code review, 2026-11-26): `filter_less_than` raises TypeError for a non-integer threshold and ValueError outside int32. `group_by_sum_count` takes NumPy ints. It checks free GPU memory (24 bytes per slot) and raises MemoryError before it allocates. `ROWS_PER_BLOCK` and `ELEMS` are set once in Python and go into the CUDA source as `#define`.
- Published benchmarks run in Windows Best performance on AC. In Balanced mode the CPU ran at about 800 to 900 MHz and Polars was up to 2x slower. The Balanced CSVs are in git history.
- The group-by sweep stops at 100M rows to keep the CPU engine runs short. A 200M check used 3.17 GiB of GPU memory, so GPU memory is not the limit.
- README References lists related work too (anilshanbhag/crystal), not only sources I read; the intro says the code is my own. cudf moved to NVIDIA/cudf (gh api redirect from rapidsai/cudf).
- Lock the GPU clocks for all published runs: SM 945 MHz (`nvidia-smi -lgc 945,945`), memory 12001 MHz (`-lmc 12001,12001`). At stock clocks the GPU changed P-state between runs and group-by times changed by 60 to 77%. A first try at 1400 MHz failed: it is not a supported step (the driver used 1402 or 1395). A clock log runs with each sweep, and samples outside 937 to 952 MHz mark the cell as off-lock.
- ncu runs with `--clock-control none`, so it keeps the lock. Its default sets a base clock (1.44 GHz), which is not the clock of the benchmarks.
- Q1 kernel: one fused kernel, the same idea as the block group-by. The 6 (returnflag, linestatus) groups are known, so there is no hash table: 36 u64 shared slots (6 groups x 6 sums), 4096 rows per block, 256 threads, one global atomic per slot per block.
- Q1 columns are encoded once (19 bytes per row) and the encoding is untimed for every engine. Each CPU engine gets its loaded table before the timer, as for filter and group-by.
- Q1 is checked against DuckDB's answer (saved CSV per SF), not pandas.
- Q1 modes are kernel_only and e2e_pinned only. Benchmark SFs are 1 and 10; SF0.01 and SF1 are for the tests.
- `exclusive_scan` checks that the int64 total fits int32 and raises OverflowError. The filter and group-by call `_scan` (no check), because 0/1 flags total at most n and the check costs a full pass over the data.
- Q1 `q1_v2` (v1.1.0): ncu showed `q1_v1` limited by shared atomics (L1/TEX 81.67%, DRAM 4.90%). Each thread keeps 36 u64 totals in registers and adds with a mask (no branch on the group). Then a warp shuffle reduce, one shared atomic per non-zero sum per warp, one global atomic per non-zero sum per block. Totals stay exact u64.
- `q1_v2` grid = SMs x blocks per SM from the occupancy API (26 x 2 = 52 blocks of 256). More blocks only add flushes; the grid-stride loop covers all rows.
- `q1_v2` layout: all 36 totals in each thread, not only the totals of a subset of groups. It uses 96 registers with no spill, and it is correct for any mix of the 6 group ids. The cost is 33% occupancy.
- `q1_v1` stays in `engine/q1.py` and in the tests and CSV, as the before point. `kernel="v1"` stays the default, so old calls do not change.
- Charts (`plot_q1.py`, after v1.2.0): horizontal bars in two panels (SF1, SF10), one bar per engine, fastest at the top, value in ms at each bar end, log x-axis. CPU engines on narrow columns only (the wide CPU times differ by 11% or less and their lines hid the narrow ones); the wide times stay in the README text. GPU bars green: `q1_v3` end to end solid #76b900, `q1_v3` kernel only #76b900 hatched, `q1_v2` end to end lighter green #b9dd85, so the two solid end-to-end GPU bars differ by more than their label. `q1_v1` is not drawn (it stays in the CSV). All five chart titles shortened to one line.
- Q1 narrow types (v1.2.0): after `q1_v2` the copy was 43.0 of 54.3 ms at SF10, so fewer bytes was the next step. price int32 cents, qty uint8 whole units (x100 when the block flushes), disc and tax uint8 hundredths, ship uint16 days since 1992-01-02 (SHIP_BASE 8036), gid uint8. `narrow()` raises ValueError if a value does not fit, so no silent wrap.
- `q1_v3` loads 4 rows per thread per step: int4 for price, uint2 for ship, one u32 for each 1-byte column. A one-row tail loop does the last n % 4 rows. The wrapper checks dtypes, contiguity and alignment (price 16 bytes, ship 8, the rest 4).
- `q1_v3` uses `__launch_bounds__(256, 2)`: 128 registers and 776 bytes of local memory, 2 blocks per SM, 4.54 ms. Without it: 156 registers, 1 block per SM, 5.71 ms (scratch runs). ncu counts 0 local spill requests.
- Narrow CPU engines (`*_narrow`) get the same narrow columns. They cast price to int64 (Polars `pl.Int64`, DuckDB `BIGINT`) before the products, and multiply sum_qty by 100 after the sum, so the answers match the wide engines exactly.
